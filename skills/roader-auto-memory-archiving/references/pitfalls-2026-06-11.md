# Pitfalls 2026-06-11 — Cron 静默兜底 + 诊断误判教训

## 🔴 P0: cron 脚本无重试 → 23:50 总结全军覆没

**症状**：
- `daily_summary.sh` 用 `set -e` + 直接 `python3 script.py`
- `vault_postprocess.py` 抛 `RuntimeError: Connection error`（Mac 睡眠/网络抖动）
- `set -e` 立即退出 → daily 文件没写 → cron 报红 → 飞书不推送但哥看不到总结

**根因**：cron 场景下 python 脚本最容易受网络影响（读 Hermes logs、scan errors.json 等），但 `set -e` 让单个失败杀整个流程。

**修复**：在 `daily_summary.sh` 顶部加 `run_py()` helper（3次重试 +静默兜底），删 `set -e`。详见 SKILL.md "Cron 脚本必须带重试 + 静默兜底" 章节。

**教训**：
1. **任何 cron 脚本里调 python 必须套重试 helper**（不限于 daily_summary）
2. **不要用 `set -e`** 当 cron 脚本里有网络读取时
3. **单次失败不刷屏**（哥规则：cron失败 >3 次告警），3次内静默

**验证命令**：
```bash
bash -n ~/.hermes/scripts/daily_summary.sh && echo "OK"
bash ~/.hermes/scripts/daily_summary.sh 2>&1 | tail -15
```

## 🟡 P1: 误把 cron 红 = hook 没触发（诊断跑偏）

**症状**：诊断「memory 系统是否正常」时，看到 `2026-06-09`之后 vault 没新归档、daily_summary cron last_status=error，第一反应猜「auto_archive_hook 没触发 / vault_postprocess 没跑」。

**实际**：是 cron 端 LLM agent 调网络时 Connection error 让 daily_summary 整个失败。**hook 端完全正常**（轮次19 / 867/2200），**postprocess 也没问题**（cron 跑 postprocess 那一步根本没轮到）。

**教训**：
1. **诊断要先分清「cron 失败」还是「hook 失败」**：`cat ~/.hermes/cron/jobs.json` 看 last_status；`auto_archive_hook.sh status` 看 hook
2. **别看到 vault 没新文件就猜 hook**——也可能是 daily_summary 端就死了
3. **修之前先跑一次 `bash script.sh` 看完整输出**，比看 cron 日志快

## 🔧 工具坑（顺手记）

- `hermes` CLI 不在默认 PATH，路径是 `~/.local/bin/hermes`
- `~/.hermes/profiles/default/` 升级后是空的（v0.16.0 改了 profile 结构），但 `~/.hermes/memories/MEMORY.md` 仍然有效（hot memory 还在跑）
- 用 `cronjob action='list'` / `hermes cron list` 查 cron 任务（不是 `cat ~/.hermes/cron/jobs.json` 直接看 JSON——后者也行但解析麻烦）
