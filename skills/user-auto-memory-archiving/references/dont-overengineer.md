# 不要过度工程 + 写作/沟通陷阱

来自 `hermes-auto-memory-archiving` v3 和 `hermes-self-improvement` v1 的合并，沉淀真实会话里**反复出现**的 4 类问题。下次冷启直接绕开。

## 1. 自造词（造词）

**症状**：自己编一个非标准术语，写进标题/标签/描述里。

**真实案例**（2026-06-08）：
- 写了 H2 标题「实时档档（实时档档钩子）」
- 「档档」是自创的叠字（"档"字叠词），结果是 "档档"+"实时" 都重复了
- 用户纠错：「这个标题有语病」

**为什么犯**：想模仿用户的口癖/语气，但没考虑可读性 + 标准术语优先。

**规则**：
- ✅ **用标准术语**（"归档" / "钩子" / "触发器"）
- ✅ **不确定用户口癖时** → 先问用户用啥说法
- ❌ **不要自造词**（叠字、谐音、生造简称）

**修复命令**（发现已写出去的词）：
```bash
# 1) 找出来
grep -rn "可疑词" ~/.hermes/skills/ ~/.hermes/scripts/ <产物>

# 2) 全局替换为标准术语
sed -i '' 's/自造词/标准术语/g' <文件>

# 3) 验证 + 归档反思到 incidents/
~/.hermes/scripts/smart_archive.sh "反思-文案语病-XXX" "..."
```

## 2. 过度工程（"要 X 只做 X"）

**用户硬规则**：**要 X 只做 X**——收到优化/调整指令时，**先问"最小改动是什么"**，然后只做那个。

### ❌ 反模式（不要做）
- 用户说"多读一份 X" → 我去重写整个 skill + 加新 skill + 改数据流
- 用户说"加 Y" → 我额外加 Z（没要的）
- 用户没让提炼 → 我主动提炼新 skill
- 用户没让改报告 → 我顺便改报告格式
- 用户说"优化 A" → 我顺带把 B/C/D 也优化了
- **我造词**（如"档档"代替"归档"）→ 用户说我自己改的，肯定要改回来

### ✅ 正模式
- 用户说"多读一份 X" → 就改 1 行加个 read 调用
- 用户说"加 Y" → 只加 Y
- 不确定时 → **先问**用户要不要扩 scope
- 看到可提炼的 → **先报告**，**不要主动**改 skill
- 写文案 → **用标准术语**（"归档"不是"档档"），除非用户明确说要口癖

### 如何判断
- 改动 >3 个文件 → ❌ 可能过度
- 改动 ≥1 个未请求的 skill → ❌ 几乎肯定过度
- 用户明确说了"X 就行" → ✅ 按 X 做，不多不少
- 我用了"我新造的词" → ❌ 改回标准词

## 3. 命名 brainstorm 模式失败

**症状**：用户问"项目叫啥英文名" → 直接给 6 个选项 → 用户全拒。

**真实案例**（2026-06-08）：
- 用户：「如果我想将这个项目共享到 GitHub 上 那应该取个什么英文名」
- 自答：先问"想突出哪点"（4 选 1：智能分类 / Obsidian / 极简 / AI）
- 用户答："智能分类 + 零丢失"
- 又给 6 个英文名（zero-loss-memory / never-forget / smart-vault / hermes-memory / obsidian-mind / palace-recall）
- 用户：「都不好 要结合 Hermes 持久化记忆」

**根因**：给了通用/泛化选项，没把"项目名 + 核心概念"显式组合。用户要的不是"哪个词好听"，是"**项目名+概念**的组合"。

**正确做法**：
1. **先确认命名维度**：问"项目名要含 Hermes 吗？""突出概念是 X 吗？"
2. **直接给组合名**，不是单字选项：`hermes-recall`、`hermes-mind`、`hermes-vault` 才是期望的形态
3. **每个选项带 1 行解释**说"为什么这个名字匹配项目"
4. **≤4 个选项**，不是 6+ 个（选项越多 → 用户越选不出）

**反模式**：
- ❌ 给泛化词（zero-loss / never-forget）—— 跟"项目身份"无关
- ❌ 给单字选项 —— 用户要的是短语组合
- ❌ 一次给 6+ 个 —— 选择过载
- ❌ 不解释为什么 —— 用户看不出差异

**推荐询问流程**：
```python
clarify(
    question="项目名要含 Hermes 吗？核心概念是 X 对吧？",
    choices=["hermes-X（推荐）", "纯 X 概念", "其他（用户说）"]
)
```

## 4. HTML 产物"花里胡哨"模式

**症状**：用户说"花里胡哨"→ 可能过度堆特效/动效/装饰，产物 1MB+。

**真实案例**（2026-06-08）：
- 用户：「给刚刚这套永久记忆方案整个花里胡哨的 HTML，包括所有的东西，以便我和其他人分享」
- 交付：31KB / 672 行 / 16 slides，**单文件可分享**
- 用户没纠错 → 这次刚好

**为什么不犯过度**：
- 用**单文件 HTML**（无外部依赖 = 分享友好）
- **紫渐变主题**沿用用户硬规则（h2 紫渐变 / h3 边框）
- **左/右/空格翻页**、**进度条**、**页码**是 PPT 风标配
- **响应式**（手机可看）

**规则**（继续这样做）：
- ✅ **单文件 HTML**（无 CDN / 无外链图片）
- ✅ **沿用用户文档偏好**（紫渐变 / 边框 / grid 目录）
- ✅ **键盘快捷键**完整（左/右/空格/Home/End）
- ✅ **进度条 + 页码**（PPT 风）
- ✅ **大小控制在 < 50KB**（邮件可发）
- ❌ 不要加视频/音频
- ❌ 不要用外网字体
- ❌ 不要堆 JS 库（jQuery/React/Vue 都不行）

## 5. 后台用 patch/read_file 被拒

**症状**：想 patch / read_file 修 skill → 工具返回 `Background review denied non-whitelisted tool`。

**事实**（Hermes logs 统计 401 条错误）：
- `patch: Background review denied` 16 次
- `read_file: Background review denied` 10 次
- `search_files: Background review denied` 4 次
- `write_file: Background review denied`（同上）

**白名单工具**（后台 review 允许）：
- ✅ `memory`（读/写热记忆）
- ✅ `skill_*`（skill_view / skills_list / skill_manage）

**解决**：
```python
# ❌ 错：后台调 patch / read_file
patch(path=..., old_string=..., new_string=...)
read_file(path=...)

# ✅ 对：后台用 skill 工具修 skill
skill_view(name='xxx')  # 读
skill_manage(action='write_file', name='xxx', file_path='SKILL.md', file_content=...)  # 写
```

**如果非用 patch 不可**（比如修普通脚本）：让用户切到主对话执行。
